# ADR 0006: 赛季三态 — 进行中 / 已暂存 / 已结束

**状态**: 已接受
**日期**: 2026-09-23

## 背景

`seasons` 表原来只有 `is_active`（0/1）一个状态位，语义是「是不是当前赛季」。
它同时承担了两个不该混在一起的职责：

1. **当前赛季是谁** —— 读接口用 `WHERE is_active = 1` 找当前赛季。
2. **赛季有没有结账** —— `/api/season/:id/end` 用 `if (!season.is_active) return 400`
   来拒绝重复结算。

于是 `POST /api/season`（新建赛季）里的这一句：

```sql
UPDATE seasons SET is_active = 0, ended_at = datetime('now') WHERE is_active = 1
```

就制造了一个**不可恢复的状态**：旧赛季被标成「已结束」（`is_active = 0`、
`ended_at` 有值），但**没有算罚金、没有写奖池流水、没有置 `prize_calculated`**。
之后想补结算也做不到 —— `/end` 看到 `is_active = 0` 就一律 400，
那句「赛季已结束」的错误信息还会让人以为一切正常。

前端也分辨不出这种赛季和正常结束的赛季：`prize_calculated` 从来没有被前端读过。

也就是说，「暂存一个没打完的赛季，先开新的」这个真实需求，
当时唯一能走的路是**静默吞掉旧赛季的罚金**。

线上数据当时还没踩到（id=7 的 `prize_calculated = 1`，罚金 30 元已入账），
但这是一颗定时炸弹。

## 决策

**把赛季状态显式建模成三态，`status` 是唯一真相：**

| `status` | 含义 | 能否录入 | 罚金 | 可否离开 |
| --- | --- | --- | --- | --- |
| `active` | 进行中 | 可以 | 未结算 | 可暂存 / 可结束 |
| `paused` | 已暂存 | 不可以 | 未结算 | 可恢复 / 可结束 |
| `ended` | 已结束 | 不可以 | 已入账 | 终态，不可逆 |

配套的六条约束：

1. **`is_active` 降级为冗余投影**，恒等于 `status === 'active'`。
   保留它是因为读接口里有几处 `WHERE is_active = 1` 不必改动。
   两列必须一起改，所以**只允许通过 `setSeasonStatus()` 写**，
   禁止在别处单独 `UPDATE ... is_active`。

2. **结算只有一份实现**：`settleSeason()`。房主点「结束赛季」和
   「建新赛季时选择结束旧赛季」两条路都调它，罚金计算、奖池入账、
   `prize_calculated = 1`、`ended_at` 一次做完。
   这是 bug 的根因所在 —— 两条路必须共用同一段代码，否则同样的坑会再挖一次。

3. **同一时刻最多一个 `active` 赛季。** 所有读接口都假设
   `WHERE is_active = 1` 只有一行（`.first()` 拿到谁是不确定的）。

4. **有歧义就拒绝，不猜。** 当「新建赛季」或「恢复暂存赛季」时已经存在
   一个进行中的赛季，而请求没带 `resolve_active`，就返回

   ```
   409 { error: '当前还有进行中的赛季，请先选择「暂存」或「结束」', active_season: {...} }
   ```

   由前端弹窗让人明确选择。带 `resolve_active: 'pause' | 'end'` 才执行。

5. **`/end` 的判据是 `status`，不是 `is_active`。**
   暂存中的赛季也允许结束 —— 语义是「这个赛季不打了，结账」。

6. **`GET /api/standings` 不带 `season_id` 时回退到最近一个赛季**，
   不再返回空。因为「当前赛季」现在可能是 `paused`，甚至一个 `active` 都没有。

新增两个接口：`POST /api/season/:id/pause`、`POST /api/season/:id/resume`
（resume 同样遵守第 4 条，并且拒绝把第二个赛季设成 `active`）。
`GET /api/seasons` 的排序改为 `active` → `paused` → `ended`，
同组内按 `started_at DESC, id DESC`。

## 理由

1. **`paused` 和 `ended` 的本质区别是罚金是否已入账。** 暂存只是「先放一边」，
   是一个纯状态动作，随时可逆；结束是一个**不可逆的账务动作**。
   把两者压进一个 `is_active = 0` 里，就等于让「暂停」和「结账」长得一模一样 ——
   这正是 bug 的成因。拆开之后，「暂存不会产生罚金」变成了类型层面的事实，
   而不是一句注释里的约定。

2. **`status` 为真相 + `is_active` 为投影，是改动量最小的正确解。**
   SQLite 不能把现有列 `ALTER` 成 `GENERATED`，重建 `seasons` 表的收益
   抵不上风险；改成由 Worker 统一维护，代价只是记住「别在别处单独写 `is_active`」。
   读接口一行不用改，线上数据一次迁移就位（见 `migration-003-season-status.sql`）。

3. **409 而不是默认行为。** 原来的默认行为（静默结束旧赛季）是错的；
   另一个看似合理的默认（静默暂存旧赛季）也不好 —— 房主可能是想结账的。
   罚金涉及真金白银，**这里猜错的代价远大于多点一下的成本**，
   所以宁可让前端多一次交互。

4. **暂存的赛季可以结束，不能凭空消失。** 如果 `paused` 赛季不允许 `/end`，
   它就会永远卡在列表里既不能结账也不能删（没有删除接口）。

## 后果

- 用户可以「暂存当前赛季 → 开新赛季 → 之后恢复旧赛季」，
  旧赛季的对局、积分、参赛选手全部保留，且**不会产生罚金**。
  这正是最初的需求。
- **前端不许读 `is_active` 判断状态**，要用 `lib/api.js` 的
  `seasonStatus(season)` / `SEASON_STATUS_TEXT`（对没有 `status` 字段的旧响应
  回退到 `is_active`）。`is_active` 是后端内部兼容层，不是 API 契约。
- 赛季列表可能出现多个 `paused` 赛季，UI 必须能同时展示和操作它们。
- `MatchPage` 的判据改为 `seasonStatus(season) !== 'active'`，
  暂存赛季的提示语是「请先新建或恢复赛季」。
- `StandingsPage` 的空榜文案按状态区分：已结束 →「本赛季没有留下对局记录」，
  已暂存 →「到「赛季」页恢复后才能继续录入」。
- 迁移会把历史数据按 `is_active` 回填：`1 → active`，`0 → ended`。
  **这是有损的**（历史数据里可能就存在那颗炸弹制造出的假 `ended`），
  但线上当时的 3 条罚金流水都对得上，没有实际损失。
- 罚金金额与平摊规则不变（见 ADR 0004），本 ADR 不触碰。
- 赛季结束后不可修改这一条继续成立（见 ADR 0003）——
  `ended` 仍然是终态，三态模型只是给它加了一个可逆的前置状态。
