# ADR 0008: 录入页拖拽排序改用 Pointer Events，不再依赖 HTML5 原生拖拽

**状态**: 已接受
**日期**: 2026-09-24

## 背景

录入成绩弹窗里的淘汰顺序原来用 HTML5 原生拖拽实现：行上挂 `draggable`，
再配 `onDragStart` / `onDragOver` / `onDrop` / `onDragEnd`。

**这套在触屏上不工作。** 手指按住行往上滑，浏览器把这一划判成页面滚动，
`dragstart` 一次都不触发 —— 于是手机上这个列表完全没法排序，只能看着。

这不是实现细节写错了，而是 API 选择错了：HTML5 拖拽是为鼠标指针设计的，
它没有定义触摸手势该怎么映射到拖拽。移动端要么靠 Pointer Events 自己实现，
要么用第三方库。

## 决策

改用 **Pointer Events**（`pointerdown` / `pointermove` / `pointerup` / `pointercancel`），
鼠标、触摸、触控笔走同一条路径。具体：

1. **落点按几何判定，不按事件目标。** 拖动时取所有行的中线，落点 = 中线离手指最近的
   那一行。行等高、重排不改变任何行的 y 位置，所以这个判据在重排前后一致
   —— 不像 `onDragOver` 那样依赖「手指此刻悬在哪个元素上」。
2. **触屏只允许从左侧把手起拖**，行内其它地方留给滚动；鼠标保持整行可拖，
   但点在「存/亡」按钮上仍是点击。
3. **把手加 `touch-action:none`。** 否则手指按住把手上下移动照样被判成滚动，
   拖拽要用的 `pointermove` 一个都不来。
4. **把手的可触范围用 `::before` 撑到 44×46，视觉占位仍保持改造前的 20px。**
5. **每次移动重新量中线**，并在手指抵住容器上下缘时自动滚动。
6. 监听挂在 `window` 上，`pointerup` 与 `pointercancel` 都收尾，弹窗卸载时也摘干净。

## 理由

**为什么触屏只从把手起拖。** 如果整行都能起拖，手指在行上滑动就变成拖拽，
列表再也滚不动了 —— 6 人时列表就比弹窗高，10 人时可滚 448px（390×844 实测），
滚动是必须保留的能力。把手是这个能力与拖拽之间的分界。

**为什么用伪元素而不是直接把把手加宽。** 第一版把把手从 20px 加到 32px，
结果是从右侧名字身上抢走了 12px：320px 宽的机器上名字被挤成 **0px**，
等于让用户盲拖。实测 320/360/390/414 四个宽度下，名字宽度分别是 0/33/63/87px。
伪元素不参与布局，于是「拇指按得准」和「不占名字的地方」可以同时成立。
实测命中区为 x 48→92、y 261→308，即 44×46。

**为什么需要自动滚动。** 10 人赛季列表高 654px、弹窗可视区 583px，
排在最后的几行一开始就在屏幕外。没有自动滚动，一个手势永远拖不到第一位 ——
只能反复「拖一下、松手、滚一屏」，那和不能拖也没差多少。
实测：从底部按住末行、抵住上缘，`scrollTop` 448→8→0，末行在同一个手势内走到第一位。

**为什么每帧重新量中线。** 自动滚动会改变各行的 y 位置，拖拽开始时量一次就作废了。
最多 10 行，每帧一次 `getBoundingClientRect`，开销可以忽略。

## 后果

- **触屏上约 15% 的行宽是拖拽专用区**（390px 下 301px 的行里有 44px），
  其余 85% 用于滚动。这是刻意的取舍，不是缺陷。
- 把手的 `z-index` 高于左侧「名次」列，所以名次列左边 6px 也能起拖。
- 拖拽期间由代码改 `scrollTop`；`touch-action:none` 只挡浏览器的原生滚动，
  不影响程序赋值。
- 未实现：跨出可视区的长距离拖拽要靠自动滚动完成（已覆盖），但没有做
  「拖动时行跟随手指位移」的浮起效果 —— 当前是原地重排 + 半透明标记。
- 触屏分支的验证靠合成 `PointerEvent`（`pointerType:'touch'`）+ 真实命中测试，
  因为本机没有 Xcode，无法用真机触摸。鼠标路径是真实指针事件端到端跑通的。
