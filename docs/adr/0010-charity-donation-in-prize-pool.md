# ADR 0010: 慈善捐赠进同一个奖池，账目上分类型而不分池子

**状态**: 已接受
**日期**: 2026-09-28

## 背景

要给奖池加一个「慈善捐赠」入口：玩家自愿捐钱，总额计入奖池，但捐赠记录要单独统计，
并按终身累计捐赠额授予称谓。

这里有一个绕不开的取舍：钱进了奖池之后，**支取时会不会被一起取走**。三种做法：

1. 同一池子、只按 `type` 分账，支取取总额。
2. 同一池子但给每笔钱打「用途锁定」标记，支取只能取罚金那部分。
3. 两个独立池子，页面上的总额只是把两个数字相加展示。

## 决策

**选 1：慈善捐赠与罚金进入同一个奖池，不分别锁定，支取取的是池子总额。**

配套决定：

- **不建 `donations` 表**，在 `prize_pool_transactions` 上加 `type='donation'`，
  `amount` 为正、`balance` 续写。「单独记录捐献列表」用 `WHERE type='donation'` 过滤实现。
- **「奖池贡献」榜只算罚金**（保持 `WHERE type='fine'` 不变），捐赠单独一张榜。
- **称谓是累计捐赠额的纯派生量**，不存储。

## 理由

**为什么不用独立表（做法 3 的变体）。** 现有余额机制是「取 id 最大那一行的 `balance` 字段」
（`getCurrentBalance`），不是 `SUM(amount)`。独立表意味着每笔捐赠要**双写**：一行进
`donations`、一行进 `prize_pool_transactions` 续 balance。两处一旦不一致，余额就永久错位，
而且没有任何机制能发现 —— 这个坑在 `worker/cleanup-test-data.sql` 里已经被记过一次。

**为什么不做「用途锁定」（做法 2）。** 需要给每笔钱打锁定标记，并让支取按锁定比例拆分，
复杂度和出错面都高一个量级。而这个系统的奖池规模是几十元、由熟人小圈子手工记账，
引入锁定机制解决的是一个不存在的问题。

**为什么贡献榜和慈善榜要分开。** 罚金是「输了交钱」，捐赠是「自愿掏钱」，语义相反。
混在一张榜上，等于把「被罚最多的人」和「最慷慨的人」并列成同一个名次序列。
`CONTEXT.md` 里「奖池贡献」的定义本来就是「累计缴纳的罚金总额」，保持不变即可。

**为什么称谓是派生量而不是存字段。** 存字段等于引入第二个真相来源，必然出现
「列表显示累计 3 元、称谓却还写着义薄云天」这种对不上的状态。派生量天然自洽，
包括删除记录导致掉档时自动回退。

## 代价（最容易被后来的人误判为 bug 的地方）

**慈善捐赠的钱可以被支取取走。** 支取一条 `withdrawal` 记录（`amount` 为负、
`player_id` 为 NULL）取走的是池子总额，其中包含捐赠。账单上**不拆分**这笔钱有多少来自
罚金、多少来自捐赠 —— 既然钱在池子里是混的，就不该假装能分清。

将来若真的需要「这笔钱只能做慈善、不能被当奖金取走」，那是做法 2，需要重做这一块。
