# ADR 0007: 末尾三名罚金 — 并列组跨越末三位边界时按档位合并平摊

**状态**: 已接受
**日期**: 2026-09-23

## 背景

`calculateBottomThreeFines` 原来是 `standings.slice(-3)`：先硬取积分最低的三个**位置**，
再在这三个里判同分。这隐含了一个从未被说出口的假设 —— **并列组不会跨过末三位这条线**。

它当然会跨。真实场景：

| 积分 | 名次 | |
| --- | --- | --- |
| 3 | 倒数第一 | |
| 8 | 倒数第二 | |
| 12 | 倒数第三 | ← 末三位窗口内 |
| 12 | 倒数第四 | ← 窗口外，但与上面同分 |
| 20 | 榜首 | |

两个 12 分并列，一个在窗口内一个在窗口外。旧实现让窗口内那位缴满 5 元、
窗口外那位缴 0 元 —— 这已经不对，但更糟的是**谁在窗口内不由罚金规则决定**，
而是由 SQL 的排序键（`ORDER BY total_score DESC, survival_count DESC`）决定。

实测：把上面那个倒数第四的 `is_survivor` 从 0 改成 1，缴费人就从李晓阳换成了赵振东。
**同一份积分、同一个赛季结果，缴费人却会变。** 这不是一个「算法不够公平」的问题，
而是一个「结果不由规则决定」的问题。

根因是 ADR 0004 那条原则没有贯彻到底。0004 写的是「同分即同排名，共享**对应排名范围**
的总罚金」—— 这句话本身是对的，但它的实现只在「位置上的三个」内部做同分比较，
所以只要并列组碰到边界就失效。

## 决策

**按并列组切分，不按位置切分。**

把积分升序排列后扫一遍，每个同分组看它落在下标 0/1/2（末三位）里的哪几席，
那几席的档位金额（倒数第三 5 元 / 倒数第二 10 元 / 倒数第一 15 元）合并成一个池子，
由**整组** —— 含界外成员 —— 平摊：

```
并列组的罚金池 = Σ 该组所占据的档位的金额
每人应缴       = 池子 ÷ 该组人数
```

金额用**分**做整数运算：并列组人数不整除池子时（7 人并列分 30 元 = 每人 4.2857…），
除不尽的分发给组内排序靠前者，保证入账总额恒等于 30 元。

## 理由

1. **这是 ADR 0004 那条原则的直接推论，不是新规则。** 0004 说的是「他们应该共享
   对应排名范围的总罚金」。两个 12 分并列倒数第三，他们的「对应排名范围」就包含
   倒数第三这一席，所以该共享这一席的 5 元。旧实现只是没有能力表达这件事。

2. **消除了一个不由规则决定的结果。** 改完之后缴费只取决于积分，与 `survival_count`
   无关；同一份战绩无论何时结算，结果都一样。

3. **总额不变，且这一点是可证的。** 三个档位恰好被所有人覆盖一次，入账恒为 30 元。
   测试里对每一组输入都断言总额等于 30 元（按分计），并穷举 1445 组无跨界并列的
   输入与旧实现逐分比对，要求完全一致。

4. **不引入新的特例分支。** 旧实现有四个 if 分支（三者同分 / 后两同分 / 前两同分 /
   都不同分）。新实现没有分支，只有一个「按并列组扫一遍」的循环，
   那四种情况都是它的自然输出 —— 少一种分支就少一个漏掉的分支。

## 后果

- 各类情形的新旧对比（积分为升序）：

| 积分（升序） | 旧结果 | 新结果 |
| --- | --- | --- |
| 3 / 8 / 12 / 16 / 20 | 15 / 10 / 5 | 15 / 10 / 5（不变）|
| 3 / 8 / 12 / 12 / 20 | 15 / 10 / 5 / 0 | 15 / 10 / **2.5 / 2.5** |
| 5 / 5 / 12 / 12 / 20 | 12.5 / 12.5 / 5 / 0 | 12.5 / 12.5 / **2.5 / 2.5** |
| 3 / 8 / 8 / 8 / 20 | 15 / 7.5 / 7.5 / 0 | 15 / **5 / 5 / 5** |
| 5 / 5 / 5 / 5 / 20 | 10 / 10 / 10 / 0 | **7.5 / 7.5 / 7.5 / 7.5** |

- **会出现非整元金额**：2.5、3.75、4.29（7 人平摊 30 元）。这是旧实现从未产生过的
  —— 旧的最细只到 12.5 和 7.5，都是二进制精确值。因此配套加了三处「收口到分」：

  | 位置 | 性质 |
  | --- | --- |
  | `settleSeason` 的余额累加 | 防御性 |
  | `/api/prize-pool/summary` 贡献榜的 `SUM` | 防御性 |
  | 前端罚金明细弹窗的合计 | **真的会飘** |

  前两处是防御性的：SQLite 的 `SUM` 带补偿求和，实测 300 条随机分位金额累加不飘。
  前端那处是真的会飘 —— `[4.29,4.29,4.29,4.29,4.28,4.28,4.28]` 直接累加得到
  `30.000000000000004`，会原样显示成「奖池入账 30.000000000000004元」。

- **历史数据不受影响。** 本 ADR 只改未来结算的计算，不回算已入账的罚金流水。
  已结束赛季的罚金按当时的规则执行并保持原样。

- **ADR 0004 不再单独维护。** 它列出的三种情况仍是新规则的真子集，
  但表述（「分三种情况」）已经过时，0004 末尾已加指向本 ADR 的说明。
