# ADR 0005: 名次展示规则 — 存活者并列第一，并列占位跳号

**状态**: 已接受
**日期**: 2026-09-22

## 背景

`match_results` 有一个 `rank` 列，但它的含义是**录入时的拖拽顺序**（`MatchPage.jsx` 的
`rank: i + 1`），不是对局名次。因为录入页把「排序」和「标记存活」做成了两个独立操作，
两者可以互相矛盾。

`calculateScores`（见 ADR 0002）只把这个顺序用于**决定淘汰者之间的先后**，存活者一律
拿最高分 `D + 1`。所以**得分一直是对的**，问题出在界面直接把 `rank` 当名次显示。

真实数据里第 20 局就是极端例子：两个已淘汰的人占了拖拽顺序的第 1、2 位，
三个存活者排在第 3、4、5 位。界面于是显示成「淘汰者第 1 名、存活者第 3 名」。

## 决策

**展示名次由「存活 + 得分」推导，不使用 `match_results.rank`：**

```
名次 = 1 + 得分严格高于自己的人数      （并列占位、跳号）
```

在 `GET /api/player/:id/details` 的 SQL 里用一个相关子查询算出，以 `rank` 字段返回，
所以前端无需改动（字段名不变），三处展示同时生效：

- 赛季页 · 个人总榜展开的逐局明细
- 赛季页 · 整赛季逐局战绩
- 积分榜页 · 展开的逐局明细

**`match_results.rank` 列保持原样**，它仍是 `calculateScores` 决定淘汰者先后的输入。

## 理由

1. **存活者必然是并列第一，且这是自动成立的**：`calculateScores` 保证存活者都拿
   `D + 1`，而淘汰者最高只有 `D`，所以存活者的得分严格最大 → 推导出的名次必然都是 1。
   不需要额外判断存活标志，也不会出现「存活者不是第一」的中间状态。
2. **并列占位跳号符合赛事惯例**（两人并列第一后直接是第 3 名），也符合用户对
   「并列第一」的直觉 —— 用户在一一对比两种方案后明确选择了 `1 1 3 4 5` 而非 `1 1 2 3 4`。
3. **只改一处**：三处展示共用同一个接口字段，后端改一条 SQL 即可，不必在前端
   三处各写一遍推导逻辑，也不会出现某处漏改。

## 后果

- 第 22 局得分 `4,4,3,2,1` → 名次 `1,1,3,4,5`；第 20 局 → `1,1,1,4,5`。
- **`rank` 字段在两个层面含义不同**：数据库列 = 提交顺序；API 响应 = 展示名次。
  读代码时不要混。API 的语义以本 ADR 为准。
- 名次是**派生值**，不落库。以后若再出现并列规则的分歧，改 SQL 即可，
  不需要数据迁移，也不影响任何历史得分。
- 积分榜总名次（`StandingsPage` 的 `i + 2`）是**另一个概念**，按数组下标排，
  本 ADR 不覆盖。若将来出现总积分与存活次数都相同的选手，那里会显示成不同名次，
  届时需要单独决定。
