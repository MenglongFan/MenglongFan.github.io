# ADR 0013: 击杀数按人头加分并入对局积分

**状态**: 已接受  
**日期**: 2026-11-05（2026-11-06 两次修订：录入交互、全局击杀额度）

## 背景

新增需求：对局中玩家每击杀一人积分加一。录入战绩时，**每个玩家有一个「击杀」按键，按几次就加几分，分数旁边有个小控件显示这一项的击杀分**。

先澄清领域边界：本系统**不存在击杀事件**，也从未记录过「谁击杀了谁」。国战里一名玩家有两名武将，「击杀一名角色」与「使一名玩家出局」并不是同一件事，而系统不记录武将、不记录阵营（`CONTEXT.md` 的「国战」词条）。因此「击杀」在本系统里无法由任何已有数据派生。

用户明确选择：**击杀数是房主为每名玩家申报的整数，不追问击杀对象、不判定某次击杀是否成立**。`CONTEXT.md` 已新增「击杀数 (Kill Count)」词条，并写明它是申报值而非事件派生量。按键累加只是这个申报值的录入方式，不改变领域语义。

这个数字直接进入 `SUM(score)`，而 `SUM(score)` 决定谁缴末尾三名罚金（15 / 10 / 5 元）。`POST /api/match` 是唯一的对局写入口，没有 PATCH / DELETE 端点，提交后误填无法自助修正。这两点共同决定了校验与录入流程的形状。

## 决策

1. **不引入击杀事件模型**。不新建 `(击杀者, 被击杀者)` 事件表，不记录被击杀者，不做同阵营判定。
2. **加分并入该局 `score`**：`calculateScores` 在 ADR 0002 的基础分与 ADR 0012 的首亮 +1 之后，给每人再加其申报击杀数。`score` 仍是唯一真值，不新增 bonus 列；总榜 `SUM(score)` 与三处逐局明细零改动。
3. **落库为逐人审计字段**：`match_results.kill_count INTEGER` + `migration-005`，历史行 NULL、不回填、不给任何读取接口返回（沿用 `migration-004` 先例）。
4. **请求体形状 `results[].kill_count`**，跟随逐人结果行。字段缺省或 `null` 视作 0；有值则严格 `Number.isInteger(n) && n >= 0`（字符串 `"3"`、小数、负数一律 400，不做静默类型转换）。**额度卡的是全场合计**：`Σkill_count <= D`，其中 `D` 是本局 `is_survivor = 0` 的人数；超额返回 400 并报出合计与 D。逐人不再设上限——额度可以给一个人，也可以分给多人。校验先于算分。
5. **缺失兼容 0 使后端可先发**：旧版 `scoring/` 产物不带该字段仍可正常录入（只是不加分），前端 build 随后补上。
6. **只对新录入的对局生效**：历史对局不重算、不补录（ADR 0003）。
7. **展示层零改动**（_2026-11-06 后补已取代此条，见文末_）：逐局明细不显示击杀数、不标注加分来源。录入页的击杀分小控件属于**录入过程**，不是明细展示（ADR 0012 后补的「亮」印章是另一回事：那是明细里的标记，不是分数拆分）。
8. **录入改为按键累加，单屏完成**：不设第二步、不设数字输入框。分数预览区里每个玩家一枚 chip，分数旁是一个小控件，显示本局击杀分 `+N`；点「杀」一次 +1，分数立即跟着涨；有值时旁边给一个「−」回退一次。**限制的是全场总额度**：预览区显示「本局击杀合计 X / D」，`Σkill_count` 达到 D 时所有「杀」一起禁用，不是每人各自封顶；切换「存/亡」让 D 变小时，从击杀数最多的人开始逐个回退，尽量保住其他人已按出的次数。
9. **击杀控件放在分数预览区，不放在拖拽行**：`.sort-item` 行尾已有「亮」「存/亡」两枚按钮，320px 下 `.sort-list` 只有 242px，行内固定项收紧后已接近上限（ADR 0008 记过「盲拖」这个失效模式），再加第三枚按钮会把 `.sort-name` 压没。`.score-preview-grid` 是 `flex-wrap`，没有宽度压力，也天然不在 `startDrag` 的 `onPointerDown` 区域内，不用改拖拽排除名单。
10. **不新增对局修改接口**。误填属运维事件，直连 D1 手工修；靠控件上的「−」与实时分数预览防误填。
11. **名次与罚金照含击杀分的新总分算**：`rank` 仍由 ADR 0005 原式派生，罚金口径不变、总额恒 30 元（ADR 0004 / 0007）。

## 与既有 ADR 的关系

> *进一步 Contradicts ADR-0005 理由 1（「存活者必然是并列第一」）：*  
> ADR 0012 的首亮 +1 已打破该前提；击杀加分幅度更大，被淘汰者可以显著反超存活者。名次算法保持原式不动，SQL 零改动。

> *Relates to ADR-0002 后果 2（「绝对分数的尺度 不影响相对排名」）：*  
> 该结论只在分数**同尺度膨胀**时成立。击杀分是按人申报的，会改变相对排名，进而改变谁缴罚金。这是明确接受的代价。

> *Relates to ADR-0012：*  
> 沿用同一套模式（加分并入 `score`、只对新对局生效）。差别在于首亮是**局级唯一指针**，击杀数是**逐人整数**，因此不需要「至多一人为真」那类唯一性校验。ADR 0012 后补已把首亮改成了明细里的「亮」印章；本 ADR 的击杀分控件只出现在录入页，不进明细。

> *Relates to ADR-0003：*  
> 不重算历史；同时明确拒绝为修正误填而引入「对局可修改」的口子。

## 考虑过的其他方案

- **手动输入数字（初版设计）**：2026-11-05 的访谈曾定为「单独一步逐人填数字 + 第二步最终分预览」。用户 11-06 更正为按键累加：数值不该由房主心算后键入，应该是按出来的；实时分数与「−」回退比事后确认页更直观。原两步流程因此取消。
- **把击杀按钮放进拖拽行**：与「亮」「存/亡」并排最直观，但 320px 下行宽不够，会牺牲玩家名字；改放 `flex-wrap` 的分数预览区后同样满足「每人一个按键 + 积分旁边一个小控件」。
- **记录击杀事件表**：信息最全、可追溯，但需新表、迁移、身份校验与同阵营判定，且与用户选定的「自由填数」相悖。
- **逐人各发一份 D 的额度（初版实现，已废弃）**：`0 <= kill_count <= D` 逐人校验，7 人场 6 死时每人都能按 6 次、全场最多发出 42 次击杀，等于把「本局淘汰了 6 个人」重复计了 7 遍。用户 11-06 指出「每人都能击杀 6 人明显不对」后改为全局额度——额度不是配给，不能按人头复制。
- **强约束 Σ击杀数 = D**：数据最自洽，但语义退回「出局 = 击杀」，等于否定了「某些击杀无人认领」的自由。取 `Σ <= D`：允许少记，不允许超发。
- **上限取 N−1 而非 D**：更贴合「打死角色但对方未出局」，但 D = 0 时仍可加分，与 ADR 0002「死亡人数决定本局价值」的口径相左。
- **独立 bonus 列 / 只改总榜汇总**：放弃原因同 ADR 0012「考虑过的其他方案」——总积分变成两处相加，或无法追溯与撤销。
- **后端宽松类型转换**：首亮代码用字符串比较是因为只做相等判断；击杀数要参与加法，照抄会把 `""` / `null` 洗成合法的 0。
- **补 `PATCH /api/match/:id` 或短时撤回窗口**：能自愈误填，但开了「对局落库后仍可修改」的口子，且重算 `score` 时罚金归属可能已变，与 ADR 0003 的边界冲突。

## 后果

- `score` 由三个来源决定：对局排名、首亮加分、击杀数。`CONTEXT.md` 的「国战」「排名积分制」「积分」「积分公式」「对局排名」「淘汰顺序」词条已同步修订。
- 每局总发放分数额外增加 `Σ击杀数`（**上界 `D`**，额度是全局的）。8 人局 5 死 3 活：A 淘汰 3 人但第 4 个出局 ⇒ 5 + 3 = 8 分，反超存活者 B 的 6 分。名次随分重排，明确接受、不是 bug。
- 一个击杀分可能让玩家跳出末三位，改变谁缴 15 / 10 / 5 元（罚金总额仍恒 30 元）。
- 已归档的 `spec-guozhan-scoring.md` 按「正文保留原样」约定不逐处改写，改在归档声明里补充过时段落清单并指向本 ADR。
- 前端 `MatchPage.jsx` 的分数预览是算分逻辑的第二份实现，必须同步加击杀分；预览与落库仍是同一个数，不再有「第一步未含击杀」的分叉。
- 明确接受的边界场景：D = 0（全员存活）时额度为 0、所有「杀」禁用；额度可以全部落在一个人身上（他确实可能包办本局所有淘汰）；首亮与击杀在同一人身上直接相加；因为不记录击杀对象，「自杀」「同阵营互杀」在本模型里无从表达，也不做校验。
- `calculateScores` 里另有一道全局额度防线：按行顺序发放剩余额度，合法请求（`Σ <= D`）下不改变任何值，别处直接调用也不会发出超过物理上限的分数。
- 回归：`calculateScores` 纯函数单测覆盖 0 死亡 / 额度分给多人 / 超额按行发放 / 首亮叠加 / 全员淘汰 / 非法值防御；源码守卫盯住全局额度校验、落库列、前后端两份公式与按键接线（含「不得有逐人上限」）。按既有约定只做单测与构建门禁，端到端由用户自测。
- 发版顺序：后端先发（向后兼容），`migration-005` 在部署前对线上 D1 执行一次，前端 `npm run build` 后发；`scoring/` 产物按既有约定只换 `index.html` 与变动的 hash 文件，字体文件不动。

## 后补（2026-11-06）：逐局明细显示击杀数标签

用户看着明细行反馈：「现在分数记录没有体现击杀分数，应该有个标签显示击杀数」。
这**取代上面决策 7**，走的是 ADR 0012 后补「亮」印章那条路。

- 形态：与「存/亡」「亮」并列一枚青绿标签，内容是 `杀N`（N = 本局该玩家的击杀数），
  `title` 写「本局击杀 N 次（+N 分）」说明加分来源。**分数仍显示最终值（如 10 分），不拆分**——
  用户要的是标签，不是 `7+3` 那类拆分（ADR 0012 后补做过同样的选择）。
- 落点：`GET /api/player/:id/details` 的 SELECT 加 `COALESCE(mr.kill_count, 0) AS kill_count`。
  不新增表列、不改已有数据、不需要新迁移；历史对局该列为 NULL → 0，前端 `> 0` 才渲染，
  不会被误标。三处明细（积分榜个人展开 / 赛季页整赛季逐局 / 赛季页个人展开）共用这个接口，
  一处 SQL 改动同时生效（ADR 0005 / ADR 0012 后补）。
- 只在有击杀时出现：0 次与历史对局都不留空标签，避免行内无意义地多一枚章。
- 窄屏：第三枚印章让 `.d-top` 变宽，360px 断点把 gap 收到 5px、标签压到 10px 字号，
  避免 320px 下把日期挤没（ADR 0008 记过这一带的溢出失效模式）。
- 决策 3「仅审计留底、不给任何读取接口返回」也一并被取代：`kill_count` 现在会进 details 接口，
  但**只用于展示**，不参与任何计算，D1 里的历史 NULL 仍然不回填。
