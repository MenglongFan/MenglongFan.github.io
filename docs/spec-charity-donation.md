# 规格文档 · 慈善捐赠

> 在奖池中引入玩家的**自愿捐赠**：总额计入奖池、记录单独统计、按终身累计额授予**捐赠称谓**。
>
> 术语遵循 `CONTEXT.md`。本文档只描述这个增量功能，不重述既有系统。
> 关键取舍已固化为 `docs/adr/0010-charity-donation-in-prize-pool.md`，实现前请先读那一份。

## Problem Statement

奖池现在只有一条进账路径：赛季结束时末位三名缴纳的**罚金**。这套机制能回答「谁被罚了多少钱」，
回答不了「谁主动掏了钱」。

现实里会出现第二种钱：有人想把上次聚会的结余放进基金池，或者单纯想请大家一次。系统里没有这个入口，
这笔钱只能记在账外——要么房主自己拿个小本子记，要么干脆不收。同时，罚金带着「输了交钱」的负面语义，
愿意额外掏钱的人在系统里得不到任何名分，长期看没有人有动力多出钱。

还有一个被现有数据规模掩盖的账目缺陷：账单面板把「不是罚金」的流水**一律显示成「支取」**。
现在只有罚金和支取两种类型，这个判断恰好成立；一旦引入第三种类型，一笔**入账**会被标成**出账**——
账本把进项标成出项，是致命的。

## Solution

在奖池上增加「慈善捐赠」这条独立的进账路径：

1. **录入**：房主指定花名册中的玩家与金额（最多两位小数），可附一句备注。
2. **同一个池子**：捐赠与罚金进同一个奖池、不分别锁定，余额是两者之和。余额下方多一行
   「其中慈善捐赠 N 元」，让房主分得清这堆钱里有多少是捐的。
3. **单独一张榜**：奖池页新增「慈善奖金」区块，按玩家**终身累计捐赠额**排序，每人显示一枚
   **捐赠称谓**。罚金的「贡献榜」保持只算罚金不变。
4. **称谓按档授予**：累计 5 / 20 / 50 / 100 元 → 解囊相助 / 仗义疏财 / 乐善好施 / 义薄云天。
   每人只显示当前最高档的一个。称谓是累计额的**纯派生量**，金额一变就跟着变，包括删记录掉档时自动回退。
5. **进流水、可追溯**：每笔捐赠都进奖池流水（账单里标成「慈善捐赠」，与罚金、支取在视觉上区分开），
   并且可以单独查看、单独删除。
6. **删除要重算余额**：删掉中间一笔，其后所有流水的余额必须重算，否则之后每一屏显示的余额都是错的，
   而且**不会自愈**。

## User Stories

### 查看慈善榜（访客，无需密码）

1. 作为访客，我想在奖池页看到一块独立的「慈善奖金」区域，所以我知道这个池子里除了罚金还有捐赠。
2. 作为访客，我想在慈善奖金区域看到累计捐赠总额，所以我知道大家一共捐了多少。
3. 作为访客，我想看到捐赠人名单（按累计额从高到低），所以我知道谁最慷慨。
4. 作为访客，我想在每个人名旁边看到他的捐赠称谓，所以「慷慨」这件事有个看得见的名分。
5. 作为访客，我想看到每个人的累计捐赠金额，所以称谓的依据是透明的。
6. 作为访客，我想在没有任何捐赠时看到一句空态文案，所以我知道不是页面坏了。
7. 作为访客，我想在奖池总余额下面看到「其中慈善捐赠 N 元」，所以我知道这个总数里有多少是捐的。
8. 作为访客，我不想在没有捐赠时看到那一行拆分行，因为它会占位置又没有信息。
9. 作为访客，我不想看到捐赠和罚金混在同一张榜上排同一个名次序列，因为「被罚最多」和「最慷慨」
   是相反的两件事。
10. 作为访客，我想不输入密码就能看慈善榜，因为它是公开信息——藏起来等于白捐。

### 录入捐赠（房主）

11. 作为房主，我想从奖池页直接进入「录入捐赠」，所以不用记接口。
12. 作为房主，我想从花名册里选捐赠人（带头像），所以不会选错人。
13. 作为房主，我想在选人时可以再点一次取消选择，所以点错了不用刷新页面。
14. 作为房主，我想输入任意大于 0 的金额，所以 3.5 元、12.34 元这种都能记。
15. 作为房主，我不想能输入三位以上小数，因为金额会累加进余额链，三位小数会让链上每个数字都变脏。
16. 作为房主，我想给这笔捐赠加一句备注（选填），所以「上次聚会结余」这类来源有地方写。
17. 作为房主，我不想备注留空时页面上出现一个空的备注位。
18. 作为房主，我想在没选人时被明确告知「请选择捐赠人」，而不是提交后拿到一个看不懂的报错。
19. 作为房主，我想在金额非法时被明确告知。
20. 作为房主，我想录入成功后直接看到「已记录 · 累计 X 元 · 称谓」，所以不用再翻一遍榜单确认。
21. 作为房主，我想录入成功后奖池余额、慈善榜、流水三处同时更新，所以不用手动刷新。
22. 作为房主，我想录入需要房主密码，所以外人不能伪造一笔入账并给自己发称谓。
23. 作为房主，我不想在录入时被要求先支取或先结束赛季，因为捐赠和赛季无关。

### 查看与删除捐赠记录（房主）

24. 作为房主，我想单独查看所有捐赠记录（逐笔），所以「单独记录捐献列表」这件事有着落。
25. 作为房主，我想在每条记录上看到捐赠人、金额、时间、操作后余额、备注。
26. 作为房主，我想删除录错的一笔，所以不用为了改一个数字去直连数据库。
27. 作为房主，我想在删除前被明确告知「奖池余额会重算、累计额与称谓也会跟着变」，
    所以我知道这不是一个局部操作。
28. 作为房主，我想删除后捐赠列表立刻反映结果，所以不会看到一条已经删掉的记录还挂在那里。
29. 作为房主，我想删除后奖池余额、慈善榜、流水一起更新。
30. 作为房主，我不想能从捐赠记录里删掉罚金或支取记录，因为罚金是赛季结算的产物、
    支取是账务动作，都不该从这里消失。
31. 作为房主，我想在捐赠记录很多时仍然能看到后面的（分页），而不是只看到前几条。
32. 作为房主，我想在删除失败时看到原因，而不是列表悄悄没变。

### 账单与账目一致性

33. 作为访客，我想在账单里看到捐赠是「慈善捐赠」而不是「支取」，因为把入账标成出账会让整个账本不可信。
34. 作为访客，我想一眼分清三种流水（罚金 / 捐赠 / 支取），所以扫一眼就知道每笔的性质。
35. 作为访客，我想在账单里看到每笔捐赠后的余额，所以能自己把账对上。
36. 作为访客，我想看到捐赠的金额显示为正数（入账），不是负数。
37. 作为房主，我想让捐赠的钱和罚金的钱在支取时不做区分，因为钱在池子里是混的，
    假装能分清只会带来更复杂的记账。
38. 作为访客，我想账单的关闭、滚动行为不因为多了捐赠类型而变化。

### 称谓

39. 作为捐赠者，我想在累计额达到 5 元时拿到「解囊相助」，所以「捐了就有名分」。
40. 作为捐赠者，我想在累计 20 / 50 / 100 元时依次升到「仗义疏财」「乐善好施」「义薄云天」，
    所以持续捐赠有意义。
41. 作为捐赠者，我想只看到自己当前最高档的一个称谓，所以不会被人名旁边挂一串名号挤爆版面。
42. 作为捐赠者，我想在删掉一笔捐赠导致累计额掉档时，称谓立刻回退，所以称谓不会和金额对不上。
43. 作为访客，我不想看到一个称谓还挂着、金额却已经掉到门槛以下。
44. 作为捐赠者，我不想称谓被单独存成一份数据，因为那迟早会和累计额对不上。
45. 作为捐赠者，我想门槛设在一次末位罚金（15 元）以下，所以捐得比罚金少也能有名分。
46. 作为捐赠者，我想恰好捐到门槛值（5.00 元）时就算达标，而不是要 5.01。

### 数据与一致性

47. 作为维护者，我想捐赠走和罚金同一张流水表（按类型区分），所以余额只有一条真相来源。
48. 作为维护者，我想在删掉一笔流水后，其后所有流水的余额被重算，所以余额链不会断。
49. 作为维护者，我想捐赠不绑定赛季，所以不会被「赛季 = 一组连续对局」这个语义套住。
50. 作为维护者，我想捐赠必须绑定花名册中的玩家，所以不存在匿名捐赠、也不存在指向不存在玩家的记录。
51. 作为维护者，我想在捐赠总额累加后收口到分，所以不会出现 `30.000000000000004` 这种数字。
52. 作为维护者，我想新增捐赠类型不需要数据库迁移，所以部署面更小。
53. 作为维护者，我想删除玩家时其捐赠记录的行为是明确的（不级联），所以不会静默丢账。

## Implementation Decisions

### 数据模型

- **不建 `donations` 表。** 在既有奖池流水表上增加一种类型 `donation`：`amount` 为正、
  `balance` 续写、`season_id` 为空。理由：余额的真相是「id 最大那一行的 `balance`」，
  不是 `SUM(amount)`。独立表意味着每笔捐赠要**双写**，两处一旦不一致余额就永久错位，
  而且没有任何机制能发现。见 ADR 0010。
- 类型列**没有 CHECK 约束**，因此新增 `donation` **不需要 schema 迁移**。
- **余额链不变式**：任一行的 `balance` = 它按 id 的前一行的 `balance` + 本行 `amount`。
  读当前余额永远取 id 最大那行的 `balance` 字段。
- **删除的不变式**：删掉第 k 行后，第 k+1 行起的每一行都要按新前驱重算 `balance`，
  在同一个批次里完成（不能只改被删那条，也不能只改最后一条）。
- 捐赠**终身累计、不绑定赛季**：`season_id` 为空。捐赠不对局，套进「赛季 = 一组连续对局构成的
  统计周期」这个语义里不通。

### 后端接口

- **奖池汇总**（公开）扩展两个字段：
  - `donation_total`：累计捐赠额，收口到分。
  - `donors`：按累计额降序，每项含玩家 id / 姓名 / 头像 / 累计额 / 笔数 / **派生称谓**。
  - 既有的 `contributions` 保持不变，**仍只统计罚金**（`WHERE type = 'fine'`）。
- **捐赠逐笔列表**（公开）：支持 `limit`（默认 100，上限 200）与 `offset`，返回逐笔记录与总笔数。
- **录入捐赠**（需房主密码）：接收玩家 id、金额、备注。
  - 校验：玩家必填且必须存在于花名册；金额必须 > 0；金额最多两位小数。
  - 备注为空时落库为固定默认串（前端据此判断「没有备注」，不要显示一个空备注位）。
  - 返回：新余额、新记录 id、该玩家新的累计额、以及新累计额对应的称谓。
- **删除单笔捐赠**（需房主密码）：只接受 `donation` 类型的记录，其它类型一律拒绝。
  删除后重写其后所有行的余额，返回新余额与被重写的行数。
- 读操作公开、写操作需房主密码——与「成绩录入、花名册管理、赛季管理、奖池支取」一致。
  捐赠是账务操作，开放录入等于任何人可以伪造一笔入账并给自己发称谓。

### 称谓

- 四档阈值与称谓字符串**只在后端存一份**，由累计额派生的纯函数计算，**不落库**。
- 前端不重复阈值，只渲染后端返回的字符串——两份阈值迟早会改歪，而且改的那天一定只改一边。
- 只返回最高档一个。理由：一行名字旁边挂四个称谓会挤爆 390px 窄屏，而且称谓的语义是
  「你现在是什么人」，不是「你拿过哪些奖」。
- 门槛从 5 元起（低于一次末位罚金 15 元），保证「捐了就有名分」。判据是 `>=`，
  恰好 5.00 元即达标。

### 前端

- **奖池页新增「慈善奖金」区块**，与「贡献榜」并列但**独立成榜**：标题行显示累计额与人数；
  列表复用贡献榜的行骨架（头像 + 姓名 + 金额），中间插一枚称谓胶囊；
  底部是两个紧凑按钮（「录入捐赠」实心、「捐赠记录」灰边）。
- **不做通栏按钮**：整页的通栏主行动是底部的「支取奖池」，再摞一条通栏就分不出主次了。
  一行只有一个视觉重点。
- **余额拆分行**：仅当累计捐赠 > 0 时，在余额数字下方显示「其中慈善捐赠 N 元」。
  为 0 时不占位置。
- **录入弹窗**：复用「赛季 → 选参赛者」那套玩家选择器（头像 + 勾），单选、再点取消。
  全应用没有下拉框，原生 `select` 在暗色玻璃面板上会长成系统控件的样子，一眼就是外来的。
- **捐赠记录弹窗**：逐笔列出，第二行右端放删除入口（**不与金额抢同一行**，窄屏上会压到数字）。
  删除走二次确认，确认文案必须写明「余额重算、累计额与称谓跟着变」。
- **弹窗必须在拿到数据之后才创建**：本项目的弹窗容器会把传入的 JSX 连同捕获的变量一起**冻住**，
  先建弹窗再往里塞数据会导致「删掉一条之后列表不变」。这条坑在赛季管理里踩过一次。
- **账单标签三分支**：罚金 → 「罚金入账」；捐赠 → 「慈善捐赠」；其余 → 「支取」。
  原来写的是「不是罚金就是支取」，加了捐赠之后会把一笔入账标成支取。
- **页面副标题**改为「末尾三名罚金 + 自愿捐赠 · 跨赛季滚存」，把第二个资金来源写在页面上。

### 与既有 ADR 的关系

- 遵循 ADR 0010。该 ADR 的「代价」段明确指出：**慈善的钱可以被支取取走**，账单不拆分来源。
  这是刻意的，不是缺陷。
- `CONTEXT.md` 中「奖池」「奖池贡献」「奖池流水」三条定义已相应更新，并新增
  「慈善捐赠」「捐赠称谓」两个词条。

## Testing Decisions

**什么算好测试。** 只断言**外部可观察的行为**：HTTP 响应体、余额数字、榜单内容、记录的存在与否。
不断言 SQL 语句形状、不断言内部函数的调用顺序、不断言 DOM 结构。测试名称使用 `CONTEXT.md`
的词汇（慈善捐赠、捐赠称谓、奖池余额、奖池贡献），不要用「donation row」这类实现词。

### 缝一（新增，唯一新缝）：Worker 的 HTTP 接口 + 本地沙盒 D1

这是能覆盖最多行为的**最高一层**：录入 → 称谓分档 → 逐笔列表 → 删除 → 余额链重写 →
贡献榜不受影响，全部经由真实请求与真实数据库完成，不 mock。
先例：本仓库既有的 `sandbox-state-machine-test` 约定（本地 `wrangler dev --local` 起沙盒，
前端用环境变量指向本地后端），以及 `worker/cleanup-test-data.sql` 记录的余额链教训。

必须覆盖的断言：

- **入账**：录入后 `donation_total` 与 `donors` 同步变化；新余额 = 录入前余额 + 金额。
- **称谓分档**：同一玩家分多笔捐到 5 / 20 / 50 / 100 的**边界两侧**，称谓逐档上升；
  边界值本身（恰好 5.00）取该档。
- **删除的余额重写**（最危险的一处）：删前记录全部行的余额快照，删后逐行比对，
  每一行都必须等于「新前驱余额 + 本行金额」。只改被删那条会留下一条断掉的链，
  之后所有展示都错且**不自愈**。
- **掉档回退**：删除导致累计额跨过门槛向下时，`donors[].title` 跟着回退；
  掉到门槛以下时返回空称谓（前端据此不渲染胶囊）。
- **互不污染**：`contributions`（奖池贡献）在捐赠前后**完全不变**；捐赠不出现在任何赛季的结算里。
- **输入校验**：不存在的玩家、金额 ≤ 0、三位以上小数、未带房主密码 —— 逐个断言被拒绝。
- **类型守卫**：拿一条罚金或支取的 id 去删，必须被拒绝。
- **不绑定赛季**：捐赠记录的 `season_id` 为空。

### 缝二（复用既有，不新增）：从源码切出的纯函数测试

先例：`worker/test/fines.test.mjs`。它把函数从源码里按两个锚点字符串**切出来**执行，
保证测的就是线上那份代码，而不是测试里重写的一份（重写等于没测）。代价是源码结构不能乱动。

称谓的档位边界同样适合这一层：无依赖、毫秒级、边界值可以穷举。

必须覆盖：`0 / 4.99 / 5 / 19.99 / 20 / 49.99 / 50 / 99.99 / 100 / 1000` 各返回哪个称谓；
负值与超大额不崩。

注意：新增的称谓表位于既有罚金测试的切片区段**之外**，因此不会影响既有测试；
但两个测试都依赖源码锚点，改动锚点会同时影响两边。

### 前端不做自动化测试

本仓库没有前端测试框架。UI 层的验证沿用既有的浏览器实机核对（起静态服务、指向沙盒后端），
只做「看得出对不对」的检查：区块是否出现、称谓胶囊文案、空态文案、窄屏不溢出、弹窗能开能关。
不进 CI。

**注意**：榜单与余额的数字用 rAF 计数动画渲染，无头浏览器会节流 rAF，
**不要断言 DOM 文本里的数字**，要和接口返回比对。

## Out of Scope

- **匿名捐赠**。捐赠必须绑定花名册中的玩家（见 `CONTEXT.md`）。
- **用途锁定**（ADR 0010 的做法 2）：让「这笔钱只能做慈善、不能被当奖金取走」。
  需要给每笔钱打标记并让支取按比例拆分，复杂度和出错面都高一个量级，
  而本系统的奖池是几十元规模、由熟人小圈子手工记账。
- **按赛季统计捐赠**。捐赠是终身累计的，不对局、不属于任何赛季。
- **编辑捐赠**。只支持删了重录。
- **玩家自助捐赠**。系统里只有房主密码，没有玩家身份，因此无法确认「这笔钱是张三捐的」。
- **称谓在积分榜 / 花名册上的展示**。这两处是已冻结的视觉，往人名旁边加元素会影响 320px
  窄屏的排版，需要单独确认后再做。
- **支取时区分资金来源**。账单不拆分一笔支取里有多少来自罚金、多少来自捐赠。
- **捐赠榜的并列名次语义**。慈善榜只按累计额降序，不引入积分榜那套 `RANK()` 跳号规则。

## Further Notes

- **页面大标题「罚金奖池」严格说已经不准确**（池子里现在有两种钱）。副标题已写明两个来源，
  但大标题没动——标题属于已冻结的视觉，改它需要单独确认。余额块上方的标签本来就是中性的
  「公共基金池」。
- **慈善的钱可以被支取取走**，这是 ADR 0010 明确记下的代价。看到「捐的钱被当奖金发掉了」
  不要当成 bug。
- **部署顺序**：必须先发后端再发前端。前端对缺失字段有兜底（拿不到累计额就按 0 处理，不会白屏），
  但调用新接口会 404。
- **实现状态**：后端四个接口、称谓派生函数、`CONTEXT.md` 术语、ADR 0010 已落地；
  前端区块、录入弹窗、捐赠记录弹窗已写完并构建通过。尚未在沙盒里跑过状态机验证，
  也尚未提交部署。
- **删除玩家时**：本仓库的表没有级联删除。删除玩家后其捐赠流水会保留（金额仍在池子里、
  账单仍显示该笔），但慈善榜是 JOIN 花名册的，该玩家的累计额会从榜上消失。这是既有行为，
  本次不改。
- **前端冻结边界**：本次改动新增了一个区块和两个弹窗，属于用户点名要的功能，不是顺手重排；
  既有的榜单、弹窗尺寸、动画时序一律未动。
